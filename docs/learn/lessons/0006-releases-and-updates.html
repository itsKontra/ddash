Releases and updates

ADR 0001 promises lockstep Releases, checksum-verified installs, and instant rollback by pinning the old image tag. This lesson follows each promise to the code that keeps it, and to one place where the code doesn't quite keep it. By the end you can walk an update or a rollback through every file it touches, and predict what happens to a Component's DB.

What a Release is

release.Build (internal/release/release.go:60) produces one flat directory, laid out like the assets of a GitHub release (doc comment at lines 1-12):

catalogue.json        every plugin.yaml + component.yaml, merged and Check()ed
SHA256SUMS            "<hex>  <file>" for every file except these two
<component>           one static binary each (CGO off, -trimpath)
<plugin>.plugin.js    copied from plugins/<plugin>/dist/
<plugin>.plugin.css

Every binary, including the core, is built with -X github.com/itsKontra/ddash/sdk.Release=<rel> (release.go:224). Lockstep comes down to that one string, and four places check it:

  • Core: cmd/ddash picks its release source from its own sdk.Release (cmd/ddash/main.go:75).
  • Catalogue: the GitHub source refuses a catalogue.json whose release differs from that tag (github.go:93).
  • Component: describe refuses a binary that reports another Release (process.go:195).
  • Browser: bundle and vendor URLs carry the Release and 404 otherwise (Lesson 5).

The trust chain

GitHubSource.Catalogue (core/runtime/github.go:74-107) downloads SHA256SUMS first, then catalogue.json. It verifies neither against anything; the trust anchor is HTTPS to GitHub. After that, ensure (github.go:179-208) checks every binary and bundle against SHA256SUMS before writing it to /data. Lesson 2's SecureConfig then checks each binary again at every launch.

This matches issue #19: HTTPS + checksums are the trust anchor; no signing in v1. The checksums catch a corrupt or truncated download, and a binary changed on disk after it was written. They can't catch a tampered GitHub release, because the attacker would publish a matching SHA256SUMS. That's what signing would add.

A file already on disk with the right checksum is never downloaded again (github.go:194). That's why installed Plugins keep running while GitHub is unreachable.

An update, step by step

The Operator changes the image tag in compose from v1.4.0 to v1.5.0 and restarts. Put the steps in order:

  1. The new core starts with sdk.Release = v1.5.0 and builds a GitHub source for that tag
  2. The catalogue on disk is v1.4.0, so SHA256SUMS and catalogue.json are fetched for v1.5.0, overwriting the old ones
  3. The reconcile loop fetches each installed Plugin's v1.5.0 bundles
  4. launch downloads each Component's v1.5.0 binary into components/<n>/v1.5.0/
  5. switchRelease copies the DB to db/snapshots/<n>.v1.4.0.db
  6. The new binary is exec'd, verified by SecureConfig, and passes Describe
  7. The SDK applies the new migrations during Start

Snapshots: one generation, and nothing deleted

switchRelease (core/runtime/snapshot.go:19) runs before every launch and compares the Release with the component_release row:

  • Same Release: it does nothing.
  • There's a snapshot of the target Release: this is a rollback. It moves the current DB into db/aside/ and restores the snapshot.
  • Otherwise: this is an upgrade. It copies the current DB to <n>.<old>.db and deletes any older snapshot, keeping one generation.

DBs in aside/ are never deleted, so a rollback loses no data on disk. Anything written after the upgrade does stop being live, though.

ADR 0001 says snapshots the old DB before a migrating update. The code snapshots on every Release change, migrating or not. That's simpler and safer, and it costs one DB copy per Component per update.

Migrations only go forward

migrate.Apply (sdk/migrate/migrate.go:46) keeps the count of applied migrations in SQLite's PRAGMA user_version, and each migration runs in its own transaction. A DB that has seen more migrations than the binary knows fails with ErrSchemaAhead: Roll back by restoring the snapshot, never by migrating down. When the SDK's openDB fails, so does Start: the Component is down until the Release changes (sdk/instance.go:178-179). Lesson 3 explained why that Down is never retried.

Exercise: is rollback really instant?

ADR 0001: The previous Release stays on disk for rollback, and rolling back (pinning the old image tag) is instant.

Reveal

The binaries and bundles for v1.4.0 are still on disk, under per-Release directories. But catalogue.json and SHA256SUMS live at the root of /data, and the update overwrote them with v1.5.0's (github.go:96-101). On rollback, local() sees a catalogue of the wrong Release and returns an error (github.go:123-124), so Catalogue goes to GitHub and fails. haveCatalogue then marks every wanted Component update pending and keeps retrying (reconcile.go:109-137). Nothing runs until GitHub answers. When it does, only the two small index files are downloaded; every binary passes the checksum check in ensure and is reused.

Update: fixed in commit 68a3af4 (#66). The index is now kept per Release in /data/releases/<rel>/. The analysis below describes the code as it was when you took this lesson.

So rollback avoids downloading binaries, but it isn't offline. A per-Release copy of the two index files (for example /data/releases/<rel>/catalogue.json) would make it work offline. Whether that's worth doing is your decision; it's the kind of ADR-versus-code gap the mission is about.

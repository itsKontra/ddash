The router

Every call that reaches a Component goes through core/router, whether it comes from a Plugin's UI or from another Component. By the end you can trace one call through either entrance, step by step, and say where it would be refused and whether the Audit Log records it.

Warm-up

Why doesn't the reconcile loop retry a Component whose Start returned Internal?

Where does the host get a Component's message types, given that it has no generated Go code for them?

Two entrances, one set of rules

The package comment (core/router/router.go:1-7) describes the whole design. A call can arrive through two entrances, and the router applies the same four rules at both: enforce requires, set the deadline, pass the actor and chain id on, and send Actions through the gate.

The two entrances establish the caller differently. Over the broker, the caller is whichever process the runtime gave that HostServer to, so a Component can't claim to be another one. Over HTTP, the Ddash-Plugin header comes from the browser and could say anything. The code says so itself: Plugins are first-party, so this guards against mistakes, not attacks (router.go:183).

Door one: a UI call, step by step

Before the router runs at all, the host's mux applies two checks to every /api/ request (core/host.go:177): guard requires a valid session, and requireConnectHeader requires Connect-Protocol-Version: 1. That header doubles as CSRF protection. A browser won't send a custom header cross-site without a CORS preflight, and ddash never grants one (host.go:196-199).

After those checks, ServeHTTP does the rest. Put its steps in order:

  1. Refuse anything that isn't POST with application/json
  2. Split the path into component and method, and compute inScope (but don't fail yet)
  3. Get the Endpoint and look up the method in the Component's service descriptor
  4. Read at most 1 MiB and decode the JSON into a dynamicpb message (unknown fields dropped)
  5. gate.Admit: write an Audit Log entry if this is an Action
  6. If refused earlier, complete the entry as failed and return the error
  7. Invoke over ep.Conn with actor and chain metadata, under a 10 s or 60 s deadline
  8. Encode the response back to JSON with the same type resolver
Why delay the refusal? The comment at router.go:84-85 says it: A refusal for scope or an undecodable request still passes an Action through the gate, as a failed entry. The Audit Log is meant to show attempts, not just successes. There's one gap: if the Endpoint lookup fails (the Component is down), the router returns at line 89, before the gate, and that attempt isn't recorded.

The gate audits before running

Gate.Admit (core/appstate/appstate.go:73) is where the descriptor from Describe pays off. IsAction(md) checks for the (ddash.action) method option (appstate.go:139):

  • Getter: admitted with a no-op done. Getters are never audited.
  • Action: an INSERT into audit_entry runs before the call. It stores the actor, the chain, the disruptive flag and the request, with fields marked secret redacted and the rest cut at 4 KiB. If the insert fails, the Action is refused with Unavailable "audit log unavailable". The gate fails closed: no audit record, no Action.
  • done(err) fills in the outcome and duration afterwards, and only while the entry is still running. On startup, Open marks entries left running by the previous host as interrupted.
This is the payoff of ADR 0002's choice. Because the host has each method's descriptor, it can tell getters from Actions and redact secret fields without any per-Component code. With an opaque Invoke(method, json), it couldn't.

Door two: the transparent proxy

HostServer builds a gRPC server with no registered services, just an UnknownServiceHandler and a raw codec (proxy.go:32-38). Every call becomes a stream of opaque frame bytes, and the codec's Name() is "proto" (proxy.go:174) so it matches what a normal gRPC peer expects.

For each call, proxy (proxy.go:40):

  1. routes the service name among the caller's requires.
  2. Unmarshals the request only if the method is an Action, for the audit entry.
  3. Calls Admit.
  4. Forwards the original bytes unchanged.

A getter's request and response are never decoded at all.

route has one subtlety (proxy.go:92-114). A required Component that isn't up yet can't report which service it serves. If some required Component is down, the caller gets that Component's error rather than PermissionDenied. Only when all its requires are up does a mismatched service mean the caller is out of scope.

Chains link the hops

Suppose a UI Action makes Component A call B. The router creates a chain id at the first hop and passes it on as gRPC metadata (onward, router.go:158). A's SDK copies it onto its outgoing calls, and forwarded reads it back at the proxy. Both hops then share a chain in the Audit Log, under the original Operator as actor. A call that arrives without metadata is A's own background work. Its actor is the Component, and it gets a new chain.

Errors speak Connect

WriteError (errors.go:41) maps each gRPC code to Connect's name and HTTP status and writes {"code","message"}. ADR 0002 requires this mapping to be exact, because Plugins use the stock @connectrpc/connect-web client and decode errors by those names.

Check yourself

1. The core DB is locked and every INSERT fails. What happens to getters and Actions?

2. Component A calls a getter on B. How many times is the request decoded into a message?

3. A Plugin calls a disruptive Action on a Component it doesn't require. Is anything audited?

4. What does requiring Connect-Protocol-Version: 1 on /api/ protect against?

The handshake

What happens between exec.Command(bin) and the *grpc.ClientConn that launch hands to Describe, and how a Component later dials back into the host. By the end you can read a Component's handshake line and predict how a launch will fail.

One call, six steps

subprocess.Launch (core/runtime/subprocess.go:41-75) makes two calls into go-plugin, client.Client() and rpc.Dispense("component"). Most of the work happens inside the first one. These are the steps, read from go-plugin v1.8.0's own source:

The library source is in your module cache: ~/go/pkg/mod/github.com/hashicorp/go-plugin@v1.8.0/. The client.go and server.go line numbers below refer to that copy.

1. The host prepares

Client.Start (client.go:580) adds go-plugin's variables to cmd.Env (client.go:638-658):

  • the magic cookie;
  • PLUGIN_PROTOCOL_VERSIONS;
  • PLUGIN_MIN_PORT and PLUGIN_MAX_PORT;
  • PLUGIN_MULTIPLEX_GRPC=true, because ddash sets GRPCBrokerMultiplex.

It then hashes the file at cmd.Path and compares the result with the SecureConfig checksum taken from the Release's SHA256SUMS (client.go:661-667). A mismatch returns ErrChecksumsDoNotMatch, and the binary never runs. With AutoMTLS, the host also generates a throwaway client certificate and passes it in PLUGIN_CLIENT_CERT (client.go:671-684).

The hash is taken just before exec. The guarantee is that the binary matches the Release's checksum as of launch. It is not a code signature.

2–4. The Component announces itself

In the child, sdk.Serve calls plugin.Serve. That function first compares the cookie variable with the expected value (server.go:259). It then listens on a fresh unix socket under /tmp and prints one line on stdout (server.go:425):

CORE | APP | NETWORK | ADDRESS | PROTOCOL | SERVER-CERT | MULTIPLEX

Try it: run a Component by hand

From the repo root:

go build -o /tmp/ntfy-api ./components/ntfy-api/cmd
/tmp/ntfy-api

You get go-plugin's refusal and exit code 1:

This binary is a plugin. These are not meant to be executed directly.

Now set the cookie and the variables a host would set:

DDASH_COMPONENT="a Component of ddash; run it from the ddash host" \
PLUGIN_PROTOCOL_VERSIONS=1 PLUGIN_MULTIPLEX_GRPC=true \
timeout 2 /tmp/ntfy-api 2>/dev/null

When I ran it, I got:

1|1|unix|/tmp/plugin3643093163|grpc||true
The certificate field is empty because no PLUGIN_CLIENT_CERT was set, so the server fell back to plain gRPC. Under the real host, that field holds the Component's certificate as base64 DER.

Map each field before reading on. 1 is go-plugin's CoreProtocolVersion. The second 1 is ddash's sdk.Handshake.ProtocolVersion. true means the server supports broker multiplexing.

5. The host dials

The host reads that first stdout line. It waits for up to StartTimeout, which defaults to one minute (client.go:398). If the line has fewer than four fields, the error is Unrecognized remote plugin message. If CORE isn't 1, it's incompatible core API version (client.go:840-866). Otherwise the host dials gRPC over the socket using the server certificate from the line.

This is why a Component must never write to stdout before plugin.Serve has printed its line. A stray fmt.Println during package init would become “the handshake line” and break the launch. Logs go to stderr: sdk/serve.go:39-43.

6. Dispense and the broker channel back

Dispense("component") calls ddash's grpcPlugin.GRPCClient (sdk/serve.go:89-96). Before returning the connection, it starts broker.AcceptAndServe(HostBrokerID, hostServer). That is the router's transparent proxy, which Lesson 4 covers, now listening as broker service 1 for this Component.

The Component side is lazy. brokerHost.dial (sdk/serve.go:108-121) calls broker.Dial(1) only on the first sdk.Require'd call. If that dial fails, the call gets Unavailable "no connection to the host", and the next call tries again.

Multiplexing matters here. Without it, the broker opens a separate connection per service ID and expects both sides to set up the service in a fixed order. The comment on HostPlugins (sdk/serve.go:64-70) explains why ddash depends on it: the Component dials only on its first Require'd call, which can be much later.

Stopping is the handshake in reverse

process.Stop (subprocess.go:105-113) calls rpc.Close(). In the child, plugin.Serve returns, and sdk.Serve gives inst.Stop 8 s to cancel the Component's context and drain its background work (sdk/serve.go:50-52). The host kills the process if it hasn't exited when its own deadline ends. The two timeouts are deliberately 8 s against 10 s, so the Component normally finishes first.

Exercise: predict, then check

subprocess.go:46 sets the child's environment like this:

cmd.Env = []string{sdk.EnvDBPath + "=" + spec.DBPath}
Reveal

All of them. ClientConfig.SkipHostEnv defaults to false, so go-plugin appends the host's entire os.Environ() to cmd.Env (client.go:655-657). It then appends its own variables after that. Every Component therefore inherits whatever is in ddash.env, including DDASH_OIDC_CLIENT_SECRET and DDASH_GITHUB_TOKEN (deploy/ddash.env.example).

Read as written, line 46 says “only the DB path”. Is that what you intended? If so, the fix is one field, SkipHostEnv: true, plus a test that a Component can't see a host variable. If Components should inherit some host settings (proxy variables or TZ, say), the fix is an explicit allowlist instead. This is exactly the kind of contract decision the mission is about, so it's yours to make.

The browser side

How a Plugin's code gets from /data into the running shell, why it has to share React and @ddash/plugin with the shell, and how each Plugin's calls reach only its own Components. By the end you can say why a Plugin page is blank, broken or refused, and which file to look in.

What a bundle looks like

Here are the first three lines of plugins/docker/dist/index.js, as pluginConfig built it (packages/vite-preset/src/index.ts):

import { definePlugin as e, useQuery as t } from "@ddash/plugin";
import { Badge as n, PageHeader as r, Stat as i, StatusDot as a } from "@ddash/ui";
import { jsx as o, jsxs as s } from "react/jsx-runtime";

And its last line:

export { Tn as default };

Those imports are bare specifiers. A browser can't resolve them by itself. Something has to say what URL "@ddash/ui" stands for, and that something is the import map.

Everything not in the map is bundled into the Plugin. That includes @bufbuild/protobuf and the Plugin's generated @ddash/proto clients. That's why the docker bundle is about 90 KB although its own code is small.

The import map makes one React

importMapPackages (packages/vite-preset/src/index.ts:12-20) lists seven packages: react, react/jsx-runtime, react-dom, react-dom/client, react-router, @ddash/ui and @ddash/plugin. The shell's Vite build puts a static <script type="importmap"> mapping each one to /vendor/__DDASH_RELEASE__/<file>.js (web/vite.config.ts:19-41). The core replaces the placeholder with the running Release when it serves index.html (core/shell.go:73-84).

The shell itself imports those packages through the same map (web/vite.config.ts marks them external too). The shell and every Plugin therefore run against the same module instances.

Why it must be one instance: React context is matched by object identity. PluginScope puts a TransportProvider in the tree using @ddash/plugin's context objects. If a Plugin bundled its own copy of @ddash/plugin, its useClient would read a different context and find no transport. Two copies of React would break hooks outright. The React docs on duplicate React describe this failure.

Caching follows from the Release in the URL

Every /vendor/<rel>/ and /plugins/<name>/<rel>/ response is sent with immutable, cached for a year. index.html is sent with no-cache (core/shell.go:22-27, versioned). An update changes the Release, which changes every URL, so browsers fetch fresh files with no cache busting. The dev Release is the exception, because make dev rebuilds in place.

The core also refuses a bundle or vendor file for any other Release with 404 (core/shell.go:41, :56). An old tab can't mix new and old code.

Loading, step by step

Put these in the order they happen when the Operator opens /docker:

  1. The core serves index.html with the Release filled into the import map
  2. The shell boots, importing React and @ddash/plugin from /vendor/<rel>/
  3. usePlugins calls ListInstalledPlugins, which returns each Plugin's script and style URL
  4. The shell appends a <link rel="stylesheet"> for the Plugin's index.css
  5. import(script): the browser fetches the bundle and resolves its bare imports through the map
  6. The default export is checked; the Plugin is stored as definition, or as error
  7. :plugin/* renders PluginPage: PluginScope, then ErrorBoundary, then useRoutes(pages)

core/shell.go:73 · web/src/plugins.ts:31-54 · core/api.go:65 · web/src/app.tsx:152-167

The shell's runtime check is loose. isDefinition (web/src/plugins.ts:56-58) only asks whether the export is a non-null object. The structural contract (an index page when nav is set, valid widget sizes, unique ids, useStatus) is enforced at build time by packages/plugin-check/src/contract.ts. Since Releases are lockstep and built by CI, the shell never needs to check it again.

Each piece of Plugin UI gets its own boundary and its own PluginScope, even the little badge in the sidebar. A badge's calls go out under its own Plugin's name, so inScope holds for them too.

The per-Plugin transport

PluginScope (packages/plugin/src/scope.tsx:64-74) creates a pluginTransport from the Plugin's name and requires. Plugin code then calls useClient(SomeService) without saying which Component it means. The transport works that out (packages/plugin/src/transport.ts:50-80):

  1. It takes the service's proto package, for example ddash.dockerapi.
  2. It finds the required Component whose name without hyphens matches: docker-api. If none matches, it throws PermissionDenied in the browser, before any request.
  3. It sends the call over a Connect transport with base URL /api/c/docker-api and the Ddash-Plugin header.
  4. It refuses streaming calls: ddash methods are unary only.

Every transport also runs requireConfirm. A call to a disruptive Action without a confirm text fails with FailedPrecondition, which makes a forgotten confirm dialog fail during development.

Only the browser enforces confirmation. The router (Lesson 4) records disruptive in the Audit Log but doesn't check that a confirm happened. As with the Ddash-Plugin header, this guards against mistakes, not attacks.

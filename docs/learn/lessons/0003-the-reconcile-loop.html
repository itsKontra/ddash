The reconcile loop

How the core decides which Components should run, and what it does when one fails, crashes or won't start. By the end you can take a failure scenario and name the state the Component ends in and what brings it back.

Warm-up

Plugin P requires A, and A requires B. Which Components can P's UI call?

Why must a Component never print to stdout during init()?

Desired state, actual state, one loop

The runtime doesn't start Components when you install a Plugin. Install (core/runtime/installed.go:29) writes a row to installed_plugin, adds the manifest to r.installed and calls poke(). That's all it does. The launching happens elsewhere, in a single loop that compares two maps:

  • Desired: order() (installed.go:198). It walks every installed Plugin's requires through the catalogue's startOrder, giving the transitive closure with dependencies first.
  • Actual: r.components. Each entry has a proc (nil until launched), a status, its crash times, held and notBefore.

Each pass of reconcile (reconcile.go:59) walks the desired order and launches every Component that isn't running yet. The check is one line (reconcile.go:86):

skip := c.proc != nil || c.held || time.Now().Before(c.notBefore)
This style is called level-triggered, the same idea as a Kubernetes controller. The loop doesn't react to individual events. Every pass recomputes the full gap between desired and actual. A missed or duplicated poke() therefore does no harm, which is why poke is a non-blocking send on a channel with a buffer of one (reconcile.go:24, runtime.go:178). Several pokes in a row collapse into one pass.

What wakes the loop

The loop sleeps in a select (reconcile.go:31-51) until one of three things happens:

  • poke(): called by Install, Restart, the runtime's own Start, and a crash timer when its delay ends.
  • The retry timer: armed only when the pass failed to launch something. It backs off from 1 s, doubling up to 5 min, and resets after a clean pass.
  • Shutdown: the context is cancelled.
One detail: the timer is created before the pass runs (reconcile.go:35). Launches are sequential, and each Start may take up to 60 s, so a slow pass can use up the backoff by itself. The next retry then comes right after it.

Uninstall works differently

Nothing in reconcile stops a Component. Uninstall (installed.go:72) does that directly. It deletes the row, recomputes wanted(), takes every Component no longer wanted out of r.components, and stops them in parallel within StopTimeout. Both functions hold the changing mutex, so a Component can never be launched and removed at the same time.

The states

A Component's State (runtime.go:33-54) combines the Component's own health (OK, Degraded, Down) with states that only the host can know. Each failure has its own way back:

The two kinds of Down

When Start fails, launch leaves the process running and returns the error as startErr, not err (reconcile.go:212). reconcile looks only at err, so it doesn't schedule a retry. On later passes, c.proc != nil means the Component is skipped. It stays Down until the Operator restarts or reconfigures it.

This matches the SDK's contract for Start (sdk/component.go:44-47): Start fails only for local reasons … report an unreachable upstream through Health instead. Retrying a local failure wouldn't fix it. A Component that returns an error from Start because its upstream is unreachable breaks this contract, and the runtime will never recover it on its own.

Health polling keeps running for a Component that failed to start. The SDK remembers the start error and answers Health with Down plus that message (sdk/instance.go:153-162), so the state doesn't drift back to Starting.

Crash backoff

watch (process.go:53) waits on proc.Done(). When the process exits, watch checks whether the runtime stopped it on purpose by comparing c.proc != proc and checking the context. If not, it records a crash time, dropping times older than 10 minutes. With 5 or more crashes in that window it sets held. Otherwise it sets notBefore = now + 1s << (n−1) and pokes the loop once the delay has passed (process.go:72-91).

Order is not readiness

reconcile launches in dependency order but does not wait for health. Launches are sequential, so B's Start has returned before A launches. B may still be Down or Degraded at that point. If B is held or backing off, A starts anyway, and any call A makes to B through sdk.Require gets Unavailable. Components are written to tolerate this: they report it through their own Health and don't fail Start.

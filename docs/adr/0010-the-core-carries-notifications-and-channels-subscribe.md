# The core carries Notifications, and channels are Plugins that subscribe

The core serves one notification service, `ddash.notification.NotificationService`, to every Component, whatever it requires: it sits on each Component's host server beside the transparent proxy (`router.Offer`), and a Component reaches it with `sdk.Notifications(env)`. A Component sends a Notification with its category (Checks, Image updates, Action outcomes). A **channel** is a Component whose API is the shared `ddash.notification.ChannelService` (`GetChannel`, `Deliver`, `SendTest`). The core finds the channels as the installed Plugins' Components whose Describe names that service (`runtime.Serving`) and delivers each Notification to every one of them that takes its category. `ntfy-api` and `telegram-api` are channels, each pulled in only by its own headless Plugin (`ntfy`, `telegram`). This replaces the `notify` Component and settles SPEC Open Decision 6. We chose this so that a channel is something the Operator installs, or doesn't. When every Plugin that sends required `notify`, and `notify` required both channels, every channel ran in every install, and a channel in trouble showed on almost every Plugin in the Catalogue. Adding a third channel now takes a Component and a Plugin, with no change to the core or to any sender.

## Considered Options

- **Senders require the channels they use, optionally**: every sender would know every channel, a new channel would mean changing every sender, and `requires` has no optional form. The Operator ruled it out.
- **Keep `notify`, with optional channels below it**: the fan-out would stay a Component every sender requires, so its state would still show on every Plugin. It would also need optional `requires`.
- **The channel answers "filtered"** (the core always calls `Deliver`): one call per channel instead of two. But every filtered Notification would be an audited `Deliver` that sent nothing. So the core asks instead: `GetChannel` (a getter, never audited) says which categories the channel takes, and only a channel that takes the category gets a `Deliver`.
- **Filters in the core's own settings**: the core would have to know each channel by name. Each channel keeps its filter in its own config, next to its destination.

## Consequences

- _Extends ADR-0002_, whose proxy routes a Component's call only to the Components it requires. The core's own services are reachable without `requires`, and a core service audits its own Actions. `Send` is an Action with target `core`, run for the actor and in the chain the sender's SDK forwarded. Each channel's `Deliver` is a hop in that same chain through the gate (`router.Hop`), as `ntfy-api Send` used to follow `notify Send`. A refused `Send` (no category) is audited too.
- Several Components can now serve one service. `route` refuses a caller that requires two Components serving the same service (`FailedPrecondition`), since its call can't say which one it means. When a refused call outside a caller's `requires` is audited, the Audit Log names the first Component by name that serves the service. No Component requires a channel, so a Component that calls `Deliver` itself is refused: only the core delivers.
- **Filters**: each channel's config has `checks`, `image_updates` and `action_outcomes`, proto3 optional bools that default to on. A config form can't hold a nested message (only top-level repeated ones), so the three fields can't be one shared message. Each channel declares them itself, and their meaning lives once, in `components/internal/channel`. A test holds every channel's config to the same field numbers, labels, help and default.
- **Delivery** goes to every channel at once, and each one gets at most `DeliveryDeadline` (20 s) for its `GetChannel` and `Deliver`. After that the core reports that channel's delivery failed, and the `Deliver` runs on to its end (ADR-0004). Its Audit Log entry records how it ended. One channel failing or hanging never fails the `Send` or holds up another channel. `Send` answers each channel's outcome (sent, failed, filtered), and fails (`Unavailable`) only when every channel that should have received the Notification failed. With no channel installed it succeeds and delivers to nobody.
- **Health**: a channel's health is its last delivery's outcome. The core polls it right after each `Deliver`, so its Plugin shows the outcome at once. Only that channel's Plugin pulls its Component in, so a failing channel shows down on its own Plugin only. `Send` itself counts toward no Component's health.
- **An installed channel is set up**: its destination is required config (ntfy's topic; Telegram's bot token and chat ID), and the "not set up" state is gone. To not use a channel, the Operator uninstalls its Plugin. An installed channel left unconfigured shows unconfigured on its own Plugin, and its deliveries fail.
- **Headless Plugins**: a `plugin.yaml` with `headless: true` has no UI of its own. The Release carries no `.ddapp` for it, installing it downloads no bundle, and `ListInstalledPlugins` gives it no script. The shell counts it as loaded with nothing to offer: no Widgets, Nav Entry, Pages, Concerns or Commands. Its Components and config forms show in the Catalogue like any others.
- The Checks Page reads the channel list through `checks`' `ListChannels`, which answers the core's list, since a Plugin's UI reaches only its own Components.
- **Upgrade**: core DB migration 0007 marks the `channel-plugins` step pending when the DB already holds ntfy-api's or telegram-api's config. On the first start with a catalogue, before the retired Components' data is dropped, the runtime installs the Plugin of each channel whose saved config names a destination. It moves the filter `notify` kept for that channel into the channel's own config. v0.0.3's wire field numbers are frozen in `core/runtime/upgrade.go`, since the core has no compiled-in types of a Component's config. The step runs once. After it, `notify` is a retired Component, and its config and Release record are dropped like any other's.
- Rolling back to v0.0.3 after this update leaves `notify` without its saved filter (all on). The channel Components keep their config, so Notifications still arrive.
